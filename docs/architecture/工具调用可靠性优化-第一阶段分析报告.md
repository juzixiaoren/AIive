## 一、当前真实调用链

```
POST /api/chat → invoke_chat() → AgentGraph.run()
  │
  ├─ 1. 构建上下文 (_build_agent_context)
  │     ├─ Stable System Contract (Kernel Contract)
  │     ├─ Core Memory Projection (L1, 精确 key)
  │     └─ Automatic Recall (L2, 语义召回)
  │
  ├─ 2. LangGraph 图执行 (_build_graph)
  │     图结构: START → assistant → policy_check → tools → assistant → END
  │     - assistant: LLM + bind_tools()，生成 resp.tool_calls
  │     - policy_check: 基于 ToolRegistry 元数据安全校验（非语义判断）
  │     - tools: LangGraph ToolNode 执行
  │     工具执行路径: ToolNode → StructuredTool → _make_handler → ToolRegistry.execute()
  │     副作用工具的 DB session: _db_handler 装饰器创建独立 SessionLocal() 并自行 commit
  │
  ├─ 3. 提取回复: messages 列表最后一个非 tool_call 的 AIMessage.content

  └─ 4. 终结处理 (_finalize, line 1348)

        │    └─ EXTRACT_ASYNC: OutboxWorker.enqueue()
        ├─ 保存 ContextSnapshot
        ├─ db.commit() (line 1504) — 唯一全局提交点
        └─ 返回 ChatResponse
```

## 二、逐项问题回答（14 项）

### 1-3. 调用链、决策位置、模型自由度

调用链见第一节。工具调用决策在 `_assistant` 节点由 `llm.bind_tools(tools)` + `resp.tool_calls` 完成——纯 LLM 决策，系统无强制机制。

### 4. 模型能否在无工具结果时生成"已完成"

**能**。`_finalize()` 直接从 LLM 输出提取 reply，无任何校验。

### 5-7. 工具结果结构、回复访问、副作用状态

- 结果三层包装：`ToolRegistry.execute()` → JSON 字符串 → `tool_records` 字典
- 回复可访问 `tool_records`，但 Runtime 不校验一致性
- 无统一副作用状态或 OperationState

### 8. 长期记忆 commit 回执

MemoryWriteService 有 `WriteResult(written: bool)`，但事务边界不一致：

| 路径 | Session | Commit 时机 |
|------|---------|-------------|
| 显式工具 (`_db_handler`) | 独立 `SessionLocal()` | handler 返回前 `db.commit()` |
| 隐式记忆 (`_finalize()` SYNC) | 共享 AgentGraph session | `_finalize()` 末尾 `self._db.commit()` |

### 9-10. 显式/隐式写入路径、异步声明

显式走 tool_calls → `_db_handler` 独立 commit；隐式走 `classify_memory_signal` → `MemoryWriteService.write()` 共享 session。两条路径完全独立。EXTRACT_ASYNC 时模型回复可能已说"记住了"，但实际写入在出站 Worker 异步执行。

### 11. 失败/超时/pending 反馈

`_tools_node` 通过 `startswith("Error:")` 和 JSON `ok` 字段判断。pending 状态不支持。

### 12. 测试覆盖

所有涉及 LLM 决策的测试使用 Mock LLM，无真实端到端验证。

### 13. 绕过路径

- `_finalize()` 直接调 MemoryWriteService — 绕过 ToolRegistry
- `_create_tool_result_events()` 直接 `db.add(Event(...))`

### 14. 系统提示词承担正确性

是。line 458 "Do not claim persistence unless a successful tool result confirms it" 是 Prompt 指令。

## 三、根因

1. **缺少 RequiredEffect 机制** — Runtime 无法区分需要副作用和不需要的请求
2. **回复与工具结果无绑定** — 回复从 LLM 输出直取，无校验
3. **无结构化 Receipt** — 状态靠文本解析
4. **显式/隐式路径独立** — 无共享状态校验
5. **测试无真实 LLM** — 无法发现"不调用但声称完成"
6. **三个决策主体各自独立** — 原生 tool_calls + classify_memory_signal + (计划新增的分类器)
7. **事务边界不一致**

## 四、推荐架构

### 4.1 总体图结构

```
START
  │
  ├─ 1. CONTEXT_BUILD (现有 _build_agent_context，不改)
  │
  ├─ 2. EFFECT_SUPERVISOR (新增，基于 ActionPlanner)
  │     职责：分析用户消息，输出本轮可能存在的 RequiredEffect 约束列表
  │     不负责规划整轮工具调用，只提供副作用约束
  │     输出存入 AgentState.effect_constraints
  │
  ├─ 3. AGENT_LOOP (保留现有 assistant → policy_check → tools → assistant 循环)
  │     主 Agent 负责动态工具选择、参数填充、多步推理
  │     Agent 不受 Supervisor 限制——可以调用 Supervisor 未列出的工具
  │     每步工具执行结果由 CapabilityExecutor 包装，产生 InvocationRecord
  │
  └─ 4. PRETERMINAL_CHECK (新增)
        职责：在 Agent 准备结束时校验 effect_constraints
        确定性行为（不是"再提醒模型一次"）：
          ├─ 约束已满足 → 放行到 FINAL_RESPONSE
          ├─ Supervisor 提供了完整合法参数 + Agent 未执行
          │     → Runtime 直接调用 CapabilityExecutor 执行（不等 Agent）
          ├─ 参数缺失或不合法
          │     → 最多一次注回 Agent，允许模型修复参数
          ├─ 修复后仍不合法
          │     → 进入澄清路径，不生成假回复
          └─ 禁止无限重试
```

### 4.2 两个决策主体，不是"统一"

| 主体 | 职责 | 输出 | 约束力 |
|------|------|------|--------|
| **EFFECT_SUPERVISOR** (ActionPlanner) | 分析用户消息，输出副作用约束 | `effect_constraints: [{capability_id, params?, required}]` | 对 Agent 是约束；对 Runtime 是执行依据 |
| **主 Agent** (LLM + tools) | 动态工具选择、参数填充、多步推理 | 实际的 tool_calls | 可以调用 Supervisor 未列出的工具 |

**冲突规则**：
- Supervisor 列出约束但 Agent 没调用 → PRETERMINAL_CHECK 介入
- Supervisor 没列出但 Agent 主动调用 → 正常执行（Agent 可能有额外发现）
- 两者参数不同 → 以 Agent 最新一次成功执行的为准（Agent 掌握最新上下文）
- Supervisor 参数缺失 → 交给 Agent 填充，一次修复机会

### 4.3 区分两层概念

| 概念 | 范围 | 状态 | 示例 |
|------|------|------|------|
| **CapabilityInvocation** | 所有工具调用 | succeeded / failed / timeout / rejected | read_text_file, memory_search, remember_or_update |
| **RequiredEffect** | 仅副作用操作 | satisfied / pending / failed / unknown | remember_or_update, schedule_reminder |

只读工具只有 `InvocationRecord`，没有 `RequiredEffect`，不存在 `committed` 概念。

**统一验证结果**（PRETERMINAL_CHECK 使用）：`PostconditionVerifier` 输出：

```
satisfied  — 副作用已确认完成
pending    — 异步中，不可声称完成
failed     — 执行失败
unknown    — 无法确认状态
```

由 CapabilityExecutor 根据工具类型映射：
- 本地 DB 写入 → `committed` → `satisfied`
- 远程 API → `confirmed` → `satisfied`
- 异步任务 → `pending`
- 失败 → `failed`

AgentGraph 只需知道 `satisfied / pending / failed / unknown`，不需要理解每种工具的 committed vs confirmed 差异。

### 4.4 EffectSource 拆分

不再用一个 enum 混淆三件事，改为三个独立字段：

```python
class RequiredEffect:
    capability_id: str
    params: dict | None            # 可为空（留给 Agent 填充）
    
    # 信息从哪来
    evidence_source: str           # user_assertion | tool_observation | system_inference
    
    # 持久化要求
    persistence_requirement: str   # user_required | system_best_effort
    
    # 执行方式
    execution_mode: str            # synchronous | asynchronous
```

| 示例 | evidence_source | persistence_requirement | execution_mode |
|------|----------------|------------------------|----------------|
| "记住我喜欢简洁回答" | user_assertion | user_required | synchronous |
| "我喜欢简洁回答" | user_assertion | system_best_effort | asynchronous |
| "以后叫我大李" | user_assertion | user_required | synchronous |
| 工具返回中提取的配置 | tool_observation | system_best_effort | asynchronous |

### 4.5 单事务写入（业务数据 + Receipt + Event）

当前 `_db_handler` 自己创建 Session 并 commit，CapabilityExecutor 在外面无法介入。

**方案 B（推荐，重构范围小）**：保持 handler 管理事务，但 handler 接收 ExecutionContext（含 effect_id），在同一事务内写入 Receipt。

```
CapabilityExecutor.execute(capability_id, params, exec_ctx):
  1. 生成 effect_id + invocation_id
  2. 创建 ExecutionContext(effect_id=..., invocation_id=..., ...)
  3. 调用 ToolRegistry.execute(capability_id, params, ctx=exec_ctx)
     → _db_handler 创建独立 Session
     → handler 在同一事务内:
        写入业务数据
        + 写入 effect_receipts 行 (通过 exec_ctx 提供的辅助函数)
        + EventLogger 写入 Event
     → db.commit()（三者同一事务）
  4. 读取 effect_receipts 确认 committed
  5. 返回 InvocationResult
```

**需修改**：
- `_db_handler` 增加 `write_effect_receipt(exec_ctx, ...)` 调用点
- handler 签名增加 `exec_ctx` 参数（已有 `ctx: RunContext`，可复用或新增）
- `ToolRegistry.execute()` 透传 exec_ctx

### 4.6 失败事务的审计

同一事务失败 = 全部回滚 = 无记录。需补充：

```
1. 短事务: INSERT operation_log(status=running, ...) → commit
   （独立事务，失败也不影响后续）
2. 业务事务: 业务数据 + effect_receipts + Event → commit
   - 成功: 更新 operation_log(status=succeeded)
   - 失败回滚: 另起短事务更新 operation_log(status=failed, error=...)
```

`operation_log` 可用现有 Event 表或新增轻量表。`effect_receipts` 仅记录已提交的成功结果。

### 4.7 PRETERMINAL_CHECK 的确定性行为

```
for each constraint in state.effect_constraints:
  if constraint.persistence_requirement != "user_required":
    continue   # system_best_effort 不阻塞
    
  matched = 查询本轮 InvocationRecord / effect_receipts
           where capability_id == constraint.capability_id
  
  if matched and postcondition_verifier.verify(matched) == satisfied:
    continue   # 已满足
  
  if constraint.params is complete and valid:
    # Runtime 直接执行，不等 Agent
    result = CapabilityExecutor.execute(constraint.capability_id, constraint.params)
    if result.effect_status == satisfied:
      continue
    else:
      # 执行失败，记录到 error_effects
      state.error_effects.append(result)
  
  elif constraint.params is incomplete:
    # 给 Agent 一次修复机会
    if retry_count < 1:
      注入结构化提示到 state，返回 AGENT_LOOP
      retry_count += 1
    else:
      # 两次都无法满足 → 澄清路径
      state.unresolved_constraints.append(constraint)

if state.error_effects or state.unresolved_constraints:
  → CLARIFICATION_RESPONSE（如实报告）
else:
  → FINAL_RESPONSE
```

关键：**这不是"再劝一次模型"**。只有参数缺失时才给 Agent 一次修复机会。如果 Supervisor 已提供完整合法参数而 Agent 漏掉了，Runtime 直接执行，不等 Agent。

### 4.8 幂等键与事实指纹分离

```python
# 通用运行时：防止同一调用因网络重试执行两遍
operation_idempotency_key = hash(source_event_id + turn_id + capability_id + call_index)

# 仅记忆领域：判断是否同一事实
# 由 MemoryWriteService 在内部使用，不存在 effect_receipts 上
# CapabilityExecutor 不负责计算 fact_fingerprint
```

`effect_receipts` 表只存 `operation_idempotency_key`（UNIQUE 约束）。`fact_fingerprint` 属于记忆领域内部机制。

```sql
CREATE TABLE effect_receipts (

CREATE INDEX idx_er_trace ON effect_receipts(trace_id);

```

### 5.2 为什么 effect_receipts 没有 fact_fingerprint

`fact_fingerprint` 是记忆领域内部概念（`canonical_key + normalized_value + scope`），用于 MemoryWriteService 内部去重/强化判断。提醒、邮件、文件等工具不使用它。两个完全相同的提醒就是用户想创建两次。因此 `fact_fingerprint` 不在通用 `effect_receipts` 表中。

## 六、各层职责

### 6.1 CapabilityExecutor（新增，Runtime 层）

```
职责：
1. 包装所有工具调用（读 + 写）
2. 生成 invocation_id，注入 ExecutionContext 到 handler
3. 对副作用工具：在同一事务内写入 effect_receipts 行
4. 调用 PostconditionVerifier 输出统一状态
5. 失败时另起短事务记录 operation_log

不负责：
- 领域业务逻辑
- fact_fingerprint 计算
- 工具参数的业务校验
```

### 6.2 MemoryWriteService（领域层，不改）

只返回 `WriteResult(written, operation, memory_id, ...)`。不感知 `EffectReceipt`。内部使用自己的去重/强化逻辑（含 `fact_fingerprint`）。

### 6.3 EFFECT_SUPERVISOR / ActionPlanner

```
职责：
- 分析用户消息
- 输出 effect_constraints 列表
- 每个约束包含 capability_id + 可能的参数（可留空让 Agent 填充）
- 不负责决定整轮所有工具调用

不负责：
- 替代 Agent 的工具循环
- 一次性规划所有操作
```

### 6.4 能力元数据（ToolRegistry 扩展）

工具返回结构化 `user_facing_result`：

```python
# 工具 handler 返回的 dict 中增加
{
    "ok": True,
    "user_facing_result": {
        "summary": "默认回答偏好已更新为简洁",   # 面向用户的摘要
        "sensitivity": "normal"                   # normal | sensitive | confidential
    },
    # 其余业务字段不变
}
```

Runtime 只负责：验证 Receipt → 允许展示 `user_facing_result.summary`。不拼接模板、不解释参数。

## 七、PRETERMINAL_CHECK 的行为矩阵

| 场景 | 行为 |
|------|------|
| Supervisor 约束 `user_required`，Agent 已成功执行 | 放行 |
| Supervisor 约束 `user_required`，Agent 未执行，但 Supervisor 提供了完整合法参数 | Runtime 直接调 CapabilityExecutor 执行 |
| Supervisor 约束 `user_required`，Agent 未执行，参数缺失 | 注入 Agent（一次机会）→ Agent 补全参数 → 重试 |
| 注入后仍无法满足 | → CLARIFICATION_RESPONSE（如实报告未完成） |
| Supervisor 约束 `system_best_effort`，未执行 | 不阻塞，Trace 中记录 extracted/pending |
| Supervisor 未列出但 Agent 主动调用副作用工具 | 正常执行（Agent 的额外发现） |
| 约束已满足，但 Agent 回复声称"已完成"而 Receipt 显示 pending | → Final Response Gate 纠正回复 |

**禁止**：无限重试、追加自然语言提示词催促模型。

### 9.5 隔离要求

- 每个独立 case 使用不同 `user_id` / `thread_id`
- 依赖 case 使用同一 thread 不同消息
- 每轮测试结束后重置测试 namespace
- 文件测试使用 fixture 创建的临时目录

### 9.6 统计与运行策略

**指标**（以总请求次数为分母）：
- Positive Tool Recall（需工具的请求中实际调用率）
- Negative Tool Precision（不需要工具的请求中不调用率）
- Memory Persistence Accuracy（记忆写入 read-after-write 成功率）
- False Success Claim Rate（声称成功但无对应 committed receipt 次数）
- Duplicate Effect Rate（同一 source_event 重复副作用次数）

**3 轮运行时**：正样本 20 × 3 = 60 次请求，报告格式 `60/60`。

**运行策略**：

| 场景 | LLM | 测试范围 | 频率 |
|------|-----|---------|------|
| 常规 CI | Fake/Deterministic | 单元测试 + Graph 状态机 + Receipt 事务 | 每次提交 |
| 架构变更回归 | 真实 LLM | 完整矩阵 1 轮 | 变更合并前 |
| 发布前验收 | 真实 LLM | 完整矩阵 3 轮 | 发布前 |
| 模型切换评估 | 真实 LLM | 完整矩阵 1 轮 | 模型变更时 |
