# 工具注入方案分析（Tool Injection Strategy）

> 日期：2026-10-22　范围：LLM 上下文中工具（capability）的注入方式、规模瓶颈与演进方案
> 依据：`runtime/context_assembler.py`、`runtime/agent_graph.py`、`tools/langchain_adapter.py`、`tools/registry.py`、`task_runtime/tools.py`、`task_runtime/runtime.py`、`task_runtime/agent_executor.py`、`task_runtime/context_assembler.py`、`control/capability_broker.py`、`desktop/registry_overlay.py`、`runtime/context_budget.py`
> 结论先行：**当前架构已是"分层注入 + 委托执行"的正确基线；真正的瓶颈在任务侧能力清单无 token 预算。推荐按 Phase 0→2 渐进演进（预算截断 → 目录 + tool_plan 预选 → 工具检索），不推荐全量 bind_tools 与代码执行式。**
>
> **2026-10-22 更新：Phase 0 + Phase 1 已落地**（分层注入 + 自主发现 + 统一能力模型），实施细节与实测结果见 §8。下文 §1–§7 保留为决策时的分析快照。

## 1. 当前工具注入机制（代码实证）

### 1.1 三条注入链路

| 链路 | 入口 | 工具面 | 注入方式 | 预算控制 | 执行边界 |
|---|---|---|---|---|---|
| 对话 Agent（chat turn） | `ContextAssembler.assemble` → `AgentGraph._prepare_execution` | **固定 5 个任务元工具**（`build_main_agent_registry`） | OpenAI function schema + `llm.bind_tools()` | `tool_definitions` 分区 soft 4000 / hard 6000 token，超限按注册序**前缀连续截断** | `ToolRegistry.execute`（直接执行 / Outbox / desktop_node） |
| 持久任务 Agent | `PersistentTaskRuntime.run` → `TaskAgentExecutor.decide` | `build_registry_for_thread().scoped(TaskScope.allowed_capabilities)` | capabilities 以 **JSON 文本塞进 user prompt**，LLM 用 **json_mode** 输出 `ActionProposal`（capability_id + arguments） | **无 token 预算**（仅 brief/state 有字符级 `_bounded_value`） | `CapabilityBroker.prepare/dispatch` → 策略 → 资源锁 → `execute_brokered` |
| 管理 / 审批旁路 | `routes_approval`、`routes_tools`、`eval/replay` | 全量注册表（+ 在线桌面节点叠加） | 不注入 LLM，直接查询/执行 | 不适用 | 同 Broker / `execute` |

### 1.2 对话侧：委托模式（delegate-first）

- `context_assembler.py:256-260`：`tool_registry = build_main_agent_registry()`，注释明确"Conversation Agent 固定只拥有任务元工具。Desktop/文件/selfdev 能力由 Persistent Task Worker 经 CapabilityBroker 获取，绝不动态叠加到主对话"。
- 元工具 5 个：`list_skills` / `delegate_task` / `get_task_status` / `cancel_task` / `send_task_input`（`task_runtime/tools.py:190-249`）。
- schema 构建与截断：`context_assembler.py:1020-1067` `_build_tools_schema_list`——超预算时按注册顺序连续截断（保留前缀，遇到装不下的工具即停止），截断结果与 token 预算单调相关。
- 绑定：`agent_graph.py:963-972` `build_langchain_tools(registry)` → 按 `assembled_ctx.tools_schema` 名称过滤 → `langchain_llm.bind_tools(tools)`。RunContext 经闭包注入 handler，不出现在 schema（`langchain_adapter.py:19-68`）。
- **含义**：36 个内置工具 + 14 个桌面能力 + MCP 桥接工具**完全不进对话上下文**；对话 LLM 每轮只见约 5 个 schema（约 1.5k token），`tool_definitions` 6000 token 预算利用率约 25%。

### 1.3 任务侧：全量清单 + JSON 提案

- 工具面计算：`runtime.py:82-83` `broker.list_capabilities(task)` → `capability_broker.py:41-47` `registry_for(task)` = `build_registry_for_thread(db, thread_id, target_node_id)`（全量注册表快照 + 在线桌面节点能力叠加，`desktop/registry_overlay.py:66-115`）`.scoped(scope.allowed_capabilities)`。
- 注入：`task_runtime/context_assembler.py:84-101`——capabilities **整体 `json.dumps` 进 user message**（`prompts.render("task_runtime.task_context", capabilities=...)`）；LLM 以 `json_mode`、temperature=0.1 输出 `ActionProposal`（`task_runtime/agent_executor.py:31-49`）。
- 执行：`broker.prepare`（TaskPolicyEngine + 生命周期闸门）→ `validate_preconditions`（TOCTOU）→ 资源锁 → `execute_brokered`（descriptor_hash 必须一致）。
- **含义**：任务侧没有 `bind_tools`，是"目录文本 + 结构化提案 + 服务端强校验"的执行式架构。这本身就是一种注入方案（可称为"全量清单注入"），且与安全边界（scope allowlist）天然对齐。

### 1.4 规模数据与预算容量

| 工具源 | 数量 | 说明 |
|---|---|---|
| 内置工具（`builtin_tools.register_builtin_tools`） | 36 | 静态，见 CODE_MAP §3.6 |
| 桌面节点能力（`desktop/protocol.py::DESKTOP_CAPABILITIES`） | 14 | 按节点在线状态动态叠加 |
| MCP 桥接工具（`mcp/bootstrap.py`） | **动态、无上界** | 每个 MCP server 可携带多个工具，安装即注册 |

- `tool_definitions` 预算 6000 token：按中等 schema 约 200-400 token/个估算，容量约 **15-30 个工具**。
- 对话侧固定 5 个，远未触限；**任务侧在 MCP 工具累积后将率先触限**，且当前无任何截断/排序机制。

### 1.5 工具过多时的现状行为

1. 对话侧：前缀截断（单调、可预期）——但固定 5 个工具，实际不会触发。
2. 任务侧：capabilities 全量进 prompt，**无预算、无截断、无排序**：
   - prompt token 随 MCP 安装数线性膨胀；
   - json_mode 下"大海捞针"，capability 选错率上升（选错 → Broker 拒绝 `capability_unavailable` 或策略 block → 任务重试或失败）；
   - 每轮 Worker 决策都付全额清单 token 成本（`renew_run` 180s 租约内的多轮决策会重复付费）。
3. `registry.scoped()` 只按 allowlist 过滤，不做相关性排序或 top-k。

## 2. 候选方案分析

### 方案 A：分层注入（静态分层 + 预算截断）——当前架构的延伸

**描述**：L0 常驻核心层（元工具，对话侧已是）→ L1 按 TaskScope/skill 静态裁剪（任务侧已是）→ L2 全量池；每层独立 token 预算，超限截断或降级到"仅目录"。

- 优点：实现成本最低（两侧均已有雏形，只差任务侧预算）；完全确定、可单测；无额外 LLM 调用；失败模式可预期（截断单调）。
- 缺点：静态边界无法按"本轮意图"自适应；被截断的工具对 LLM 不可见（可能正是该用的那个）；层边界需人工维护，MCP 动态工具会持续冲击 L1/L2 边界。
- 判定：**作为基线长期保留**，是其他方案的地基。

### 方案 B：LLM tool_plan 注入（两阶段：目录 → 计划 → 完整 schema）

**描述**：第一轮只注入"工具目录"（capability_id + 一句话描述，约 30-50 token/个），LLM 输出本轮需要的工具 shortlist（tool_plan）；第二轮仅把选中工具的完整 schema 注入，再正式产出 `ActionProposal`。

- 优点：token 成本与工具总数**解耦**（O(目录) + O(选中)）；选型注意力集中，选错率下降；与任务侧"提案式"架构天然契合（目录本来就在 prompt 里，改造集中在 `TaskContextAssembler` 与 `ActionProposal`）；目录可压缩（按 skill 预过滤后通常 <50 条）。
- 缺点：多一次 LLM 调用（延迟 + 成本，可用轻量模型/缓存缓解）；目录本身仍随工具数增长（但增速低一个数量级）；漏选需要 fallback（未选中但需要的工具 → 下一轮 expand，或 Broker 拒绝后带错误反馈重选）；对 json_mode 的单轮决策协议有侵入（需定义两阶段 schema）。
- 判定：**任务侧能力面 >20 时启用的主力方案**。

### 方案 C：渐进式披露 / 工具检索（目录常驻 + 按需 expand）

**描述**：目录常驻上下文；LLM 通过 `describe_tool(name)` 或 `search_tools(query)` 元工具按需拉取完整 schema（ToolFormer / tool-search 模式），可多轮 expand。

- 优点：token O(目录) + O(按需)，支持数百工具规模；交互自然，漏选可自救。
- 缺点：多轮往返（拉取→调用），延迟敏感场景吃亏；实现复杂（元工具 + schema 缓存 + 会话内可见性状态）；与 json_mode 单轮决策的任务侧不兼容（任务侧可组合 B+C：目录预选 + 详情拉取）。
- 判定：**对话侧未来若开放大工具面时的选项**；当前对话侧固定 5 工具，无需启用。

### 方案 D：代码执行式（工具即代码 API）

**描述**：LLM 生成代码，在沙箱内调用工具 API 并组合结果（code-execution with tools 模式）。

- 优点：token 最省；多步组合无需多轮往返。
- 缺点：与现有安全架构冲突最大——Broker、TaskScope、审批流、descriptor_hash 防漂移都挂在"工具调用边界"上，代码执行会绕过或必须重建这套边界；沙箱基础设施成本；评测确定性下降（eval replay 24 场景依赖固定工具面）。
- 判定：**不推荐作为主线**。桌面节点侧可作远期评估项，且必须先解决 scope/审批在代码路径上的等价物。

### 方案 E：混合路线（推荐）

**基线 A 不动，按数据增长分阶段叠加 B/C，永不采用 D。**

## 3. 方案对比

| 维度 | A 分层注入 | B tool_plan 两阶段 | C 渐进披露/检索 | D 代码执行式 |
|---|---|---|---|---|
| token 成本 | O(本层全部) | O(目录)+O(选中) | O(目录)+O(按需) | O(最低) |
| 选型准确率 | 中（注意力被摊薄） | 高（两阶段收敛） | 高 | 高 |
| 延迟 | 无额外调用 | +1 次调用 | +N 次往返 | 沙箱启动开销 |
| 实现成本 | 低（已有雏形） | 中（任务侧协议改造） | 高（元工具+状态） | 很高（安全重建） |
| 与 Broker/审批/descriptor_hash 兼容 | 完全兼容 | 完全兼容（预选不越 scope） | 完全兼容 | 冲突，需重建等价物 |
| 确定性 / 可测试性 | 高 | 高（目录与 plan 均可快照） | 中（多轮状态） | 低 |
| 失败模式 | 截断丢工具（可见降级） | 漏选（可重试兜底） | 漏 expand（可自救） | 沙箱逃逸/部分执行 |
| 对 MCP 动态工具适应 | 差（冲击层边界） | 好（目录线性增长慢） | 好 | 中 |
| 适用位置 | 两侧基线 | 任务侧主力 | 对话侧远期 | 不采用 |

## 4. 推荐落地路线

### Phase 0（立即，低风险，纯服务端）

1. **任务侧 capabilities 加 token 预算与截断**：把 `context_assembler._build_tools_schema_list`（对话侧）的预算截断模式提取为共享函数，任务侧对 `broker.list_capabilities()` 结果按预算截断（建议先在 `AIIVE_CONTEXT_BUDGET_JSON` 增加 `task_capabilities` 覆盖项，复刻 chat 侧配置模式）。
2. **按 skill/task_type 预过滤**：`skill.capabilities` 与 task_type 最小 profile 已存在（`skills/catalog.py`、`TaskScope.from_brief`），把"不填 allowed_capabilities 时的默认全量"改为"skill/task_type 最小 profile 优先"，显式 allowlist 仍最高优先。

### Phase 1（短期，任务侧主力）

3. **目录 + tool_plan 两阶段**：`TaskContextAssembler.messages` 将 capabilities 拆为"目录"（id + 一句话，常驻）与"完整 schema"（按 plan 选中注入）；`ActionProposal` 增加 `tool_plan: list[str]` 阶段输出；未选中但 Broker 拒绝时，把"可用 capability 目录"随错误反馈重选（已有 `capability_unavailable` 错误路径，扩展为重选提示）。
4. **观测先行**：在 `llm_calls` / 任务 run snapshot 中记录 `capability_count`、`selected_count`、prompt token 分布，用数据触发 Phase 2。

### Phase 2（中期，按数据触发）

5. **工具检索 top-k**：对 capability 描述做 BM25/embedding 检索（与记忆检索管线**分开实现**，避免耦合），把"目录"替换为"检索命中的 top-k 完整 schema"；对话侧若未来开放大工具面，叠加 C 的 `search_tools` 元工具。

### 明确不做

- 全量 bind_tools（36+14+MCP 全进对话上下文）——token 浪费且拉低选型准确率；
- 代码执行式——安全边界重建成本超过收益。

## 5. 与现有安全架构的兼容性

- **注入层只影响"可见性"，不影响"可执行"**：所有执行仍走 `ToolRegistry.execute` / `CapabilityBroker.dispatch` / `execute_brokered`，scope allowlist、TaskPolicyEngine、审批、descriptor_hash 防漂移全部在工具边界上生效。因此注入方案可以激进演进，无需改动安全内核。
- **红线**：tool_plan/检索的预选结果**不得引入 scope allowlist 之外的工具**；预选只是"建议看哪些"，Broker 的 scope 校验是最终裁决。
- **eval 影响**：`eval/replay.py` 的 24 个场景直接调 `get_tool_registry().execute`，不经过注入层；但若 Phase 1 改了任务侧协议，需同步检查 `test_agent_task*` 与 `test_capability_broker*` 的断言。
- **回滚**：每个 Phase 独立开关（预算数值、两阶段协议版本），可逐项回退而不影响其他阶段。

## 6. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 前缀截断丢掉的正是所需工具（A） | 截断顺序按注册序 = 确定性；对话侧固定 5 工具无此问题；任务侧 Phase 0 截断时按"skill profile 优先 + 注册序"排序，降低丢失概率 |
| tool_plan 漏选导致多一轮调用（B） | 漏选时 Broker 错误反馈携带目录，重选一次；统计漏选率纳入观测 |

| 观测缺失导致盲目演进 | Phase 1 第 4 条先行：先有 `capability_count/selected_count/token 分布` 数据再触发 Phase 2 |

## 8. 实施落地（2026-10-22）

### 8.1 统一 Agent 能力模型（取消 task_type / Skill Profile 收窄）

- `task_runtime/router.py::normalize_task_brief` 不再用 `default_capabilities(task_type)` 预置能力白名单；
  未显式给出 `allowed_capabilities` 时写入 `scope.capability_policy="unified"`。
- `control/scope.py::TaskScope` 新增 `capability_policy`（unified/restricted）：
  - `unified`：`allows_capability()` 恒真，`CapabilityBroker.registry_for()` 返回全部可用能力；
  - `restricted`：显式 `allowed_capabilities` 仍是硬白名单（用户/调用方真实授权）。
- **真实约束全部保留**：`validate_arguments` 的 `allowed_roots`（路径）、`allowed_hosts`（域名）、
  `allow_network`、`allow_secrets`、节点在线状态，以及 `TaskPolicyEngine` 的 network/secret/high-risk 判定不变。
- Skill 只提供指令与 `requires_network`；`delegate_task` 未显式给能力列表时标记 unified，
  Skill 的 capability 列表仅作为展示/兼容信息，不再限制发现与执行。

### 8.2 ToolRegistry 职责分层（`tools/registry.py`）

| 接口 | 职责 | 是否含 Schema |
|---|---|---|
| `register` / `unregister` | 注册、卸载；`descriptor_hash` 仍由注册时计算 | — |
| `catalog()` | 轻量目录：id、描述、来源、风险、审批/网络/删除标记、指纹、执行器 | 否 |
| `search(query, limit=5)` | 本地关键词检索（id > 描述 > 参数名，确定性排序，CJK 二元组展开） | 否 |
| `definition(id)` | 单工具完整定义（`parameters` / `input_schema` / 安全属性 / 指纹） | 是 |
| `list_all()` | 管理 API / 诊断；docstring 明确禁止整段注入模型上下文 | 是 |
| `execute` / `execute_approved` / `execute_brokered` | 执行链不变 | — |

目录与检索每次读取实时注册映射，无独立索引缓存，注册/卸载/重注册立即生效。

### 8.3 分层注入（`task_runtime/tool_injection.py`）

- L0 常驻：`memory_search`、`memory_timeline`、`memory_event_log`、`web_search`、
  `search_knowledge`、`run_shell`（本机真实 bash，见 §9）、`desktop_exec`（仅节点在线时存在）、
  `list_tasks`、`cancel_task`。
- 注入模式：
  - `mode=full`：可执行目录 ≤ `FULL_INJECTION_MAX_TOOLS(12)` 且总字符 ≤ 24k → 全部注入完整 Schema；
  - `mode=discovery`：超出后只注入常驻完整定义，其余按需发现，避免持续注入全量 Schema。
- `TaskContextAssembler.snapshot()` 用 `tools` 取代旧 `capability_ids` 与全量 `capabilities`：
  `tools.mode / resident / available / discovered / loaded`。
- `tools.discovered` 与 `tools.loaded` 只保存 id 与定义指纹，注入时按当前注册表重建：
  工具卸载 → `unavailable`；`descriptor_hash` 变化 → `definition_changed`（不返回旧 Schema）；
  检索结果消失的 id → `removed`；每条附带 `in_scope`。

### 8.4 自主发现协议（沿用 JSON ActionProposal）

`ActionProposal.decision` 新增两个**只读**取值：

- `{"decision":"search_capabilities","query":"..."}` → 在**全量可用目录**检索（内置 + 在线桌面 + MCP + 自进化），
  返回 id + 摘要 + `in_scope`；不受 task_type / Skill Profile 限制。
- `{"decision":"describe_capability","capability_id":"..."}` → 返回完整定义并记录指纹。

两者由 `PersistentTaskRuntime._record_discovery` 处理：不创建 `AgentAction`、不调用任何 handler、
不经过 Broker 派发；仅写 `task_state.tool_discovery` 与内部事件，并计入 `usage.discovery_steps`。

## 9. 本机 Bash 执行（`run_shell`）

- 接入方式：`tools/builtin_shell.py::handle_run_shell` → `tools/local_shell.py::run_bash`，
  以 `bash -c <command>` 子进程执行，**不依赖 Desktop Node**。
- Shell 解析：`resolve_bash()` 顺序为 显式配置（`AIIVE_SHELL_BASH_PATH`）→ `shutil.which("bash")`
  → 常见 Git Bash 安装路径；全部失败返回 `shell_unavailable`，**不回退** cmd/powershell。
  返回体里的 `shell.version` 为 bash 自报版本（本机实测 GNU bash 5.2）。
- 安全链：注册为 `local_builtin`、`risk_level=medium`、`writes_external_world=true`、
  `effect_mode=non_repeatable_external`；执行仍经 `CapabilityBroker` → `TaskScope`（cwd 必须在
  `allowed_roots`）→ `TaskPolicyEngine` → 审批 → 资源锁 → `execute_brokered`。
- 命令分级（`tools/shell_policy.py`）：单条、无 `; | & > <` 等复合操作符且可执行文件在只读白名单
  （ls/cat/grep/git status 等）→ 直接放行；其余（rm/mv/git push 等）→ 审批；curl/wget/ssh 等 →
  还必须 `allow_network`，否则拒绝。git 仅放行 status/log/diff/branch 列举等只读子命令。
- 路径作用域：`shell_path_violations()` 解析命令参数里的路径（绝对路径 / `~` / `..` / 含分隔符的相对路径），
  按 `cwd` 解析后必须落在 `allowed_roots` 内，否则 `block:shell_path_outside_task_scope`——
  避免"只读白名单"变成任意路径读取通道（`cat /etc/passwd`、`cat ../secret`）；
  含 `$VAR` / 反引号的动态路径无法静态判定，降级为审批而不是直接放行。
  Windows 上 Git Bash 的 `/c/foo` 形式会先还原成 `C:/foo` 再比较，避免作用域内路径被误判。
- 资源控制：`timeout_seconds`（默认 60s，上限 300s）到点终止整个进程树（POSIX 进程组 /
  Windows `taskkill /F /T`）；stdout/stderr 各保留 `shell_max_output_bytes`（默认 64KiB），
  超出截断并标记 `truncated`；子进程环境只透传白名单变量（密钥类变量一律不传入）。
- 返回结构：`ok / exit_code / stdout / stderr / timed_out / duration_ms / truncated / cwd / shell`。
- 验证：`tests/unit/backend/test_local_shell.py` 30 例（真实执行、非零退出、cwd、超时终止、
  截断、环境隔离、bash 缺失不回退、分级策略、路径越界与动态路径降级、任务内审批与路径拦截）。
