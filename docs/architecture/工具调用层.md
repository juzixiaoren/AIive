# 工具调用可靠性与长期记忆真实性优化任务

请优化当前 Agent 的工具调用架构，重点解决以下问题：

> 模型有时会在自然语言中声称“我记住了”“已经保存”“已经完成”，但实际上没有调用对应工具，或者工具没有成功执行。

本任务不能通过关键词匹配、硬编码测试语句或单纯修改系统提示词解决。目标是建立架构级保证：

> 需要产生真实副作用的请求，必须实际调用对应工具并获得成功结果；只有成功结果存在时，Agent 才能向用户声明操作已经完成。

---

## 一、工作方式

本任务分为两个阶段。

### 第一阶段：只分析并提交方案

首先完整阅读：

* 项目编码规范；
* Agent 主循环、Graph、Planner、Dispatcher、Tool Registry；
* 工具调用协议与工具执行节点；
* 最终回复生成路径；
* 长期记忆写入、更新、遗忘和查询路径；
* Runtime State、Trace、Event、Outbox；
* 相关测试和数据库模型；
* 当前系统提示词和工具描述。

第一阶段只允许：

* 阅读代码和文档；
* 运行只读检查；
* 运行现有测试；
* 定位真实调用链；
* 输出修改方案。

禁止：

* 修改代码；
* 修改数据库；
* 创建 migration；
* 修改系统提示词；
* 增加关键词规则；
* 提前实施任何修复。

方案必须先交给用户确认。用户确认后才能进入第二阶段。

---

## 二、第一阶段必须回答的问题

请先定位并报告：

1. 用户请求从进入系统到最终回复的完整调用链；
2. 模型在什么位置决定是否调用工具；
3. 工具调用是否完全依赖模型自由选择；
4. 模型能否在没有工具成功结果时直接生成“已完成”类声明；
5. 工具结果通过什么结构返回；
6. 最终回复生成节点能否访问本轮真实工具结果；
7. 是否存在统一的副作用状态或 operation state；
8. 长期记忆写入是否有真实 commit 回执；
9. 显式记忆请求和隐式长期偏好分别如何进入写入流程；
10. 自动记忆提取是否可能异步执行，但模型却在当前轮声明成功；
11. 工具失败、超时、拒绝和 pending 状态如何反馈；
12. 当前测试是否只检查模型文本，而没有检查真实工具调用和最终持久化状态；
13. 当前有哪些路径绕过统一 Tool Registry、Capability Executor 或 Memory Write Service；
14. 当前系统提示词是否承担了本应由 Runtime 保证的行为正确性。

然后给出：

* 根因分析；
* 推荐架构；
* 预计修改模块；
* 数据流变化；
* 兼容风险；
* 测试方案；
* 清理方案。

不要假设具体文件名、类名或框架结构。所有修改位置必须以实际阅读到的代码为依据。

## 三、目标行为

### 1. 需要副作用的请求

当请求需要改变持久化状态或外部状态时，Agent 必须实际调用对应工具或注册能力。

例如：

* 写入、更新或遗忘长期记忆；
* 修改文件；
* 创建任务或提醒；
* 更新项目状态；
* 调用外部系统；
* 执行任何其他真实动作。

不能只用自然语言回答“好的”“已完成”“我记住了”。

### 2. 不需要副作用的请求

解释、分析、假设、闲聊和当前上下文足以直接回答的问题，不应为了通过测试而滥用工具。

本任务不是要求所有请求都调用工具，而是要求：

> 所有确实需要工具的请求都可靠调用工具。

---

## 四、推荐的架构目标

请根据当前项目结构设计最合适的实现，但最终必须满足以下架构性质。

### 1. Required Effect

模型的结构化决策必须能够表达：

* 当前请求是否需要真实副作用；
* 需要哪一种能力；
* 该副作用是否为完成当前请求的必要条件。

示意语义：

```text
required_effect:
  type: memory.write
  required: true
```

具体字段、模型和位置由你根据现有架构决定，不要机械照抄示例。

模型负责理解用户语义，Runtime 负责保证所声明的必要副作用真正执行。

### 2. 统一工具执行入口

所有真实副作用必须经过项目现有的统一工具或能力执行入口。

禁止：

* 在回复生成代码中直接修改数据库；
* 为测试单独增加旁路写入；
* 绕过 Tool Registry 或统一执行器；
* 仅修改状态变量伪造工具成功；
* 用模型回复文本代替实际工具执行。

### 3. 真实执行回执

工具执行后必须产生结构化回执，至少能够表达：

* operation ID；
* capability/tool；
* requested / executing / committed / pending / failed 等状态；
* 创建或修改的对象 ID；
* 错误原因；
* 是否已完成持久化。

只有实际提交成功才能视为 `committed`。

“模型打算调用”“已经生成 tool call”“已进入异步队列”都不等于执行成功。

### 4. Postcondition Check

当某个副作用是完成请求的必要条件时，Runtime 必须在最终回复前检查：

* 对应工具是否实际执行；
* 回执是否属于本轮 operation；
* 状态是否成功；
* 必要的持久化状态是否存在。

如果没有成功回执：

* 不得把该请求标记为完成；
* 不得声称“已经记住”“已经保存”“已经修改”；
* 应根据真实状态报告 pending、failed 或未执行。

### 5. Final Response Gate

最终回复必须和真实工具结果一致。

推荐实现机械化的最终结果校验，而不是只依赖模型自觉。

不要主要依靠扫描以下自然语言：

* “记住了”
* “保存成功”
* “已经完成”

自然语言表达无法穷举。

优先使用：

* 结构化最终决策；
* effect claim 与 receipt 绑定；
* operation ID 对应检查；
* Runtime 根据结果渲染简单确认信息。

具体实现由你结合现有 Agent Graph 决定。

## 五、长期记忆的特殊要求

### 1. 显式记忆请求

当用户明确要求长期保存、更新或遗忘信息时：

* 必须走同步或可确认完成的记忆工具路径；
* 必须通过统一 Memory Write Service 或现有正式写入入口；
* 必须获得数据库成功提交回执；
* 成功后才能回复“已记住”或“已更新”；
* 失败时必须准确报告失败；
* pending 时不能声称成功。

### 2. 隐式长期记忆

以下表达可能没有“记住”二字，但语义上可能要求形成稳定长期记忆：

```text
我喜欢简洁一些的回答。
以后技术问题先给结论。
你以后叫我大李。
这个项目后续统一使用 PostgreSQL。
以后处理代码问题先定位，不要直接修改。
```

是否属于长期记忆必须由模型进行语义判断，禁止使用关键词、正则、消息长度或固定短语表判断。

一旦模型判断该事实需要持久化，本轮 Trace 中必须出现真实的长期记忆写入工具或对应注册能力调用。

### 3. 普通后台提取

如果系统还有普通对话后的异步记忆提取：

* 异步任务可以继续存在；
* 当前轮不能因为“已排队”就声称长期记忆已经保存；
* 只有 committed 后才算真实持久化；
* UI、Trace 或后续查询应能看到最终状态。

### 4. 真实持久化验证

长期记忆测试不能只检查工具返回文本。

必须进一步验证：

* `memory_records` 或项目实际长期记忆真相源中存在对应记录；
* lifecycle/validity 状态正确；
* canonical key、scope 或等效字段正确；
* 工具结果中的 ID 可以重新读取；
* 重试不会重复写入或错误强化；
* 同一用户事实不会因自动提取和显式工具调用被重复计算。

## 六、禁止事项

### 1. 禁止自然语言硬编码

禁止添加或扩大任何类似逻辑：

```python
if "记住" in message:
    call_memory_tool()

if "我喜欢" in message:
    save_preference()

if "以后" in message:
    sync_memory()

if "报错" in message:
    skip_memory()
```

同样禁止：

* 关键词表；
* 正则语义分类；
* 消息长度阈值；
* 中文、英文短语枚举；
* 针对测试用例文本的特殊判断；
* 为某些领域维护固定触发词；
* 通过工具名称字符串猜测用户意图。

允许的硬规则仅限结构事实，例如：

* operation 是否存在；
* receipt 是否成功；
* event 是否已经处理；
* tool 是否注册；
* 参数是否符合 schema；
* 持久化事务是否提交。

### 2. 禁止以系统提示词作为主要修复

默认禁止修改、追加或动态注入系统提示词。

不能通过加入以下提示来冒充修复：

```text
“用户要求记住时必须调用工具”
“不要忘记调用工具”
“禁止没有调用工具就说完成”
```

这些内容可以作为辅助提示，但不能成为正确性的主要保证。

正确性必须来自：

* 结构化决策；
* Runtime 路由；
* 工具执行；
* 成功回执；
* Postcondition Check；
* Final Response Gate。

### 3. 系统提示词例外

只有当架构调整确实需要模型理解新增的结构化协议或工具语义时，才可以提出最小系统提示词修改。

但在第一阶段方案中必须单独说明：

* 为什么 Runtime 无法独立解决；
* 需要增加的准确文本；
* 该文本承担什么辅助作用；
* 为什么它不是主要正确性保障；
* 不增加该文本会发生什么。

未经用户确认不得修改。

### 4. 禁止针对测试过拟合

生产代码不得：

* 读取测试输入列表；
* import 测试数据；
* 根据测试 case ID 处理；
* 为 20 条测试请求添加特殊分支；
* 通过修改测试降低验收要求；
* mock 主验收中的 LLM 或工具结果；
* 伪造数据库记录、Trace 或 receipt。

## 七、真实 LLM 端到端验收

修改完成后，必须使用项目实际配置的真实 LLM 运行端到端测试。

单元测试可以 mock LLM，但最终验收禁止 mock。

### 1. 测试数量

至少发送 20 条确实需要调用工具的真实用户请求。

这 20 条请求必须覆盖多个领域。

其中：

* 长期记忆领域不少于 8 条；
* 其他工具领域不少于 12 条；
* 非记忆请求至少覆盖 4 个不同的现有工具或能力领域；
* 所有请求只能使用项目真实存在的工具，禁止虚构工具。

优先使用安全、可回滚、可清理的操作。

### 2. 长期记忆测试组成

至少 8 条长期记忆请求中：

* 至少 3 条可以明确表达保存、更新或遗忘意图；
* 至少 5 条不能明确包含“记住”“保存到记忆”等直接提示词；
* 这 5 条必须是模型需要通过语义理解识别的稳定信息或长期约束。

隐式记忆测试应覆盖不同语义，例如：

* 用户身份或称呼；
* 稳定表达偏好；
* 长期工作方式；
* 项目长期决策；
* 稳定习惯；
* Agent 后续行为约束。

不要只把同一种句式替换名词后重复测试。

### 3. 其他领域测试

其余至少 12 条工具请求应根据项目当前真实工具选择，覆盖不同领域，例如：

* 文件读取或修改；
* 项目状态；
* 搜索或外部信息；
* 任务或提醒；
* Runtime 状态；
* 日历、邮件或消息；
* 代码、测试或环境操作；
* 其他已注册能力。

如果项目没有其中某个工具，使用其他真实存在的能力替代。

禁止为了凑领域新增假工具。

## 八、每条测试的通过条件

一条测试只有同时满足以下条件才算通过：

1. 请求确实需要工具；
2. Trace 中出现预期工具或注册能力的真实调用；
3. 工具使用合法参数；
4. 工具实际执行，而不是只生成 tool call；
5. 工具返回成功结果；
6. 最终回复与真实工具结果一致；
7. 模型没有在工具成功前声明完成；
8. 没有调用错误领域的工具；
9. 没有依赖关键词硬编码；
10. 副作用可以从实际状态重新验证。

长期记忆请求还必须额外满足：

1. 实际调用长期记忆写入、更新或遗忘能力；
2. 数据库或实际真相源中可以 read-after-write；
3. 内容、类型、scope 和状态符合用户语义；
4. 同一事实没有重复写入；
5. 最终回复只有在 commit 成功后才确认记住；
6. 工具失败时不会声称记住。

不能仅凭最终回复中出现：

```text
“已记住”
“已经处理”
“完成”
```

判定测试通过。

本任务通过标准：

```text
真实 LLM 工具请求总数：不少于 20
实际工具调用成功率：20/20
最终状态验证成功率：20/20
长期记忆请求：不少于 8
长期记忆真实持久化成功率：8/8
隐式长期记忆请求：不少于 5
隐式长期记忆工具调用成功率：5/5
错误成功声明次数：0
遗漏工具调用次数：0
工具调用后未执行次数：0
工具失败却声称成功次数：0
重复记忆写入次数：0
测试关键词硬编码：0
依靠系统提示词作为主要修复：0
```

任何一项未达到，任务不得标记完成。

不能使用“绝大部分通过”“模型存在随机性”“后续再优化”作为验收结论。

失败时必须：

* 保留失败 Trace；
* 报告真实失败原因；
* 修复架构；
* 重新运行完整的至少 20 条真实 LLM 验收；
* 不得只重跑失败样本后宣称整体通过。

## 十一、失败注入测试

除 20 条成功路径外，还必须测试至少以下失败场景：

1. 长期记忆工具返回失败；
2. 数据库 commit 失败或事务回滚；
3. 工具超时；
4. 工具返回 pending；
5. 模型没有生成必要 tool call；
6. 模型尝试在无 receipt 时声称成功；
7. receipt 属于其他 operation；
8. 同一 operation 被重试；
9. 显式工具和自动提取处理同一个事实；
10. 一条消息包含多个记忆事实，但仅部分写入成功。

失败场景的通过标准不是工具成功，而是：

* 系统不伪造成功；
* 最终回复准确反映 failed/pending/partial；
* 状态没有脏写入；
* 可以安全重试或恢复。

* 新增自然语言正则；
* 新增 `if substring in message`；
* 新增系统提示词；
* 动态 system message 注入；

* 绕过 Memory Write Service 的记忆写入；

* 未绑定 operation ID 的成功声明。

发现上述内容时必须说明用途。

凡承担语义识别或成功确认的硬编码必须删除。
