## 1. 本轮做了什么

### 1.1 CI 接入 ruff（第一轮 §4 第 1 项）

`.github/workflows/ci.yml` 新增 `ruff` job：

```yaml
- name: 运行 ruff
  run: ruff check backend/aiive --select F,E9
```

只把「未定义名 / 语法错误」这类真实缺陷设为门禁，风格项（UP037、B023、BLE001 等）不阻断，
与 `docs/CODE_MAP.md` §10.5 的本地基线口径一致。

### 1.2 顺序依赖防线（第一轮 §4 第 5 项）

新增 `scripts/check_single_file_tests.sh`：

- 对 `tests/` 下每个 `test_*.py` 单独起一个 pytest 进程；
- 根 `conftest.py` 用 PID 命名 SQLite 库，因此多进程并发互不干扰；
- 任一文件单独运行失败即退出非零，并打印该文件日志尾部；
- 支持 `PYTHON_BIN` / `JOBS` / `PYTEST_TARGETS` 环境变量，本地与 CI 共用同一脚本。

CI 新增 `single-file` job 调用该脚本（`JOBS=2`）。此前只有 `test_v2_recall` 与
`test_tool_calling_runtime` 两个抽样点，现在覆盖全部 91 个文件。

### 1.3 basedpyright 告警清零（第一轮 §4 第 2 项）

第一轮遗留 66 条 warning，主体是域模块 re-export 私有 `_handle_*` 触发的
`reportPrivateUsage` / `reportUnusedFunction`。处理方式：

| 改动 | 范围 | 兼容性 |
| --- | --- | --- |
| handler 改公开名 `handle_*` | 10 个 `builtin_*.py` 领域模块 | `builtin_tools` 用 `handle_x as _handle_x` re-export，tests / selfdev 的 `_handle_*` 引用不变 |
| 共享机制改公开名 `db_handler` / `require_ctx` | `builtin_tools.py` + 6 个使用方 | `SessionLocal` 仍与 `db_handler` 同模块，monkeypatch 契约不变 |
| 删除多余 `# pyright: ignore` | mcp 2 个文件、task_runtime/repository.py | 这 8 条已被 pyright 判为 unnecessary，删除后仍 0 error |
| `func.max` 空表判断类型收窄 | `retrieval/retrieval_index.py::next_index_version` | 运行期语义不变（空表仍返回版本 1），仅把 `int` 误判改为 `int \| None` |

没有关闭或放宽任何 pyright 规则，`pyproject.toml` 的 `[tool.basedpyright]` 未改动。

## 3. 关键决策

| 决策 | 理由 |
| --- | --- |
| 域模块用公开名、`builtin_tools` 保留私有别名 | 消除跨模块私有引用，同时不破坏 tests 对 `_handle_*` 的既有引用（测试归用户维护，本轮零测试改动） |
| 单文件防线做成脚本而不是内联 CI 命令 | 本地与 CI 用同一份逻辑，失败时能直接复现；也避免 YAML 里堆 bash |
| ruff 只开 `F,E9` 门禁 | 风格项在第一轮已记录为「既有」，现在设为门禁会让历史风格问题阻塞无关改动 |
| 修 `func.max` 的恒真比较而不是 ignore | 该处 `row[0]` 运行期确实可能为 NULL，按 `int \| None` 收窄比压告警更准确 |

## 5. 后续开发必要信息（增量）

- **新增 handler 的命名**：领域模块写 `def handle_xxx(...)`；在 `builtin_tools.py` 的导入块里写
  `from aiive.tools.builtin_<domain> import handle_xxx as _handle_xxx`，注册表继续用 `_handle_xxx`。
  不要反过来（在域模块写私有名）——那会重新引入 reportPrivateUsage。
- **需要 DB 的 handler**：装饰器是 `@db_handler`（公开名），从 `aiive.tools.builtin_tools` 导入；
  side-effect 工具用 `require_ctx(ctx, "tool_name")`。
- **提交前自查**：
  ```
  ruff check backend/aiive --select F,E9
  basedpyright
  python -m pytest tests/unit tests/flow      # 日常
  bash scripts/check_single_file_tests.sh     # 改动涉及夹具 / 模块级状态时
  ```
- **单文件脚本注意**：它按 `find tests -name 'test_*.py'` 取文件，新增测试目录会自动纳入；
  日志写到临时目录并在退出时清理，不会污染工作区。

## 7. 坑点与可复用经验

> 按「现象 → 根因 → 下次怎么做」记录。多数坑的共性是：**本地环境与 CI 环境不等价**，
> 以及**工具链的默认行为会静默吞掉失败**。

### 7.1 环境与工具

| 现象 | 根因 | 下次怎么做 |
| --- | --- | --- |
| `.venv/Scripts/python.exe -m basedpyright` 报 `No module named basedpyright` | basedpyright 只装在全局 `E:/python/Scripts`，不在项目 venv | 直接用 `/e/python/Scripts/basedpyright`；ruff 则走 `.venv` |
| 本地 basedpyright 0 error，CI 却 11 errors | CI 的 basedpyright job 只装 pyright、不装项目依赖；缺依赖会让 `import aiive.*` 退化成 `reportImplicitRelativeImport` | 类型检查 job 必须 `pip install -e ".[dev]"`；怀疑环境差异时用 `basedpyright --pythonpath <无依赖解释器>` 复现（本次复现出 931 errors，与 CI 注解同型） |
| 拿不到 CI job 日志（无 gh / 无 token） | 公开仓库的 job 日志接口需要 admin 权限 | 先 `GET /actions/runs/{id}/jobs` 看 steps + conclusion 定位到具体步骤；需要日志内容就让 workflow 在失败时 `echo "::error::..."`，再读 `/actions/runs/{id}/annotations_partial` |
| `git push` 报 `Recv failure: Connection was reset` | 本机直连 GitHub HTTPS 不通 | 走本地代理 `-c http.proxy=http://127.0.0.1:7897`；`api.github.com` 可直连（且与代理 IP 的限流互不影响） |

### 7.2 容器与 CI 流水线

| 现象 | 根因 | 下次怎么做 |
| --- | --- | --- |
| docker-smoke 在「构建镜像」4.5 分钟失败 | Dockerfile 把 apt/pip/npm 源写死国内镜像，境外 runner 跨境超时 | 镜像源用 `ARG` + compose build-args，CI 传官方源，本地默认值不变 |
| docker-smoke 在「执行数据库迁移」失败 | 应用 lifespan 启动时已自动 `alembic upgrade head`，CI 又并发跑一次 | 先等 `/health` 通过，再做幂等的 `alembic upgrade head` 校验 |
| docker-smoke 后端启动即退出 | compose 设 `HOST=0.0.0.0`（非 loopback），Settings 拒绝 `.env.example` 的默认开发令牌 | 冒烟测试注入一次性占位令牌；本地用「同镜像 + 全新 pgvector 容器」复现比等 CI 更快 |
| 冒烟脚本改完不知道有没有生效 | 只看 job 红绿无法区分步骤 | 用 `docker build --check`、`docker compose config` 先做静态校验，再靠 jobs API 看步骤级结论 |

### 7.3 Git 与 shell

| 现象 | 根因 | 下次怎么做 |
| --- | --- | --- |
| `git add <路径> && git commit ...` 后 `git log` 没有新提交，push 却说 up-to-date | `git add` 对「已忽略但已跟踪」的路径报错退出，`&&` 链在 commit 前中断 | 提交与推送分成两条命令，逐步看 exit code；改完先 `git status --short` 确认暂存区 |
| 终端输出把多行挤成一行，像是 sed 把文件改坏了 | 输出渲染/CRLF 显示问题，文件本身没坏 | 用 `git diff` 或 `cat -A` 复核，不要凭终端显示判断文件损坏 |
| `sleep 150` 的等待命令返回空、日志没进展 | 工具默认超时 60s，命令被中断 | 长等待显式设 timeout，或用 `run_in_background` + 短轮询 |
| `sed 's/\\b_db_handler\\b/db_handler/g'` 把日志字符串 `[TRACE:_db_handler]` 也改了 | 全局替换会命中字符串/注释 | 替换后 `grep` 目标文件复核；日志/协议字符串单独排除 |

### 7.4 测试

| 现象 | 根因 | 下次怎么做 |
| --- | --- | --- |
| 单文件隔离脚本「看起来」能跑，但失败时可能不报错 | 只测了通过路径 | 用 `/tmp` 下必然失败的临时用例验证退出码为 1（本次已验证） |
| `pytest -m unit` 不生效 | pytest 9 的 marker 过滤先于 conftest 打标 | 层级筛选一律用目录：`pytest tests/unit` |
| 集成层用例偶发读不到数据 | 集成层需要多会话读同一物理库 | 集成层用 `db` 夹具；`db_session` 只给单元/流程层 |
